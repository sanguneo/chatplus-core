# chatplus-core 후속 작업 계획

작성 2026-10-03. 이 문서는 **구현 지시가 아니라 다음 세션의 결정 완비 작업 계획**이다.
여기에 나열된 미래 기능은 이름이 적혔다는 이유로 구현되지 않는다. 각 작업은 별도
승인과 별도 실행으로 진행한다.

## 0. 표기법과 증거 등급

| 기호 | 뜻 | 신뢰 근거 |
| --- | --- | --- |
| ⊨ | 이 저장소에서 **실측**된 사실 | 명령 출력·테스트·실제 읽기 |
| ⚠ | **가정**. 반증 전까지만 유효 | 추론·외부 문서 |
| ⊢ | **증명 의무**. 구현 전에 충족해야 함 | 미충족 |

규칙: ⊨ 는 그 측정이 덮는 범위에서만 주장한다. 좁은 측정으로 넓은 결론을 내리지
않는다. CRC 일치는 인증이 아니고, 두 번 읽어 같다는 것은 원자 스냅샷이 아니다.

## 1. 이상 상태 · 현재 델타 · 비목표

### 1.1 소비자와 이상 상태
- **소비자 A (saya / 클라이언트)**: 자체 `openapi.json`을 바이트로 핀하고, 선언된
  기능만 그린다. 이상 상태: 방·메시지·(향후)스트림·발송을 손실 없이, 불확실을
  불확실로 정직하게 받는다.
- **소비자 B (코어 운영자 = 사용자 본인)**: 자기 PC의 채팅+ 로컬 캐시를 읽기 전용으로
  본다. 이상 상태: 실행 중 클라이언트를 건드리지 않고, 비밀은 디스크로 새지 않는다.

### 1.2 현재 상태(⊨)와 델타
- ⊨ 읽기 전용 HTTP 코어: `/capabilities`, `/rooms`, `/messages`, `/openapi.json`.
  Bearer 인증(토큰 SHA-256 상수시간 비교), 루프백 바인딩, 접근 로그 off.
- ⊨ 저장소 해독: Credential Manager `key_.`(16바이트)로 `.secure` cipher-key 파일을
  AES-GCM 인증 복호 → URL-safe Base64 → 32바이트 Hive 키. Hive 값은 AES-256-CBC+PKCS7,
  프레임 CRC seed = `crc32(sha256(HiveKey))`.
- ⊨ 검증(2026-10-03, `com.sktelecom.torchlight` 1.5.4.6): basedpyright 0, ruff 통과,
  포맷 정상, 합성 테스트 77 통과, 실제 캐시 43방·140메시지(본문 109)·발송 0,
  실제 루프백 TCP 서버 무인증 401 / 인증 200 / 방 43.
- **델타(미구현)**: 페이지네이션 커서, SSE 스트림/재개, 발송, 첨부 다운로드, saya 연결,
  스냅샷 세대 일관성, 계정 epoch 신원, 미지 버전·어댑터의 가용성 정책.

### 1.3 비목표 (Must-NOT-Have)
- 로그인·토큰 갱신·RCS 프로토콜 재구현. 로그인 우회. 임의 테스트 메시지 발송.
- 실제 대화/번호/연락처/키를 소스·테스트·로그·커밋에 포함.
- 외부 저장소 공개/푸시. tsuba·kanao·saya 레포 수정.
- 근거 없는 정확성 주장(§9).

## 2. 형식 모델

### 2.1 프레임 재생과 tombstone 의미론
로그를 프레임 열 `L = (f_1,…,f_n)`, `f_i = (k_i, v_i)`, `v_i ∈ Bytes ∪ {⊥}`로 본다
(`⊥` = 빈 암호문 영역 = 삭제). `decode_frames`는 좌→우 폴드다.

```
S_0 = ∅
S_i = S_{i-1} with k_i ↦ v_i   (v_i ≠ ⊥)
    = S_{i-1} without k_i        (v_i = ⊥)
결과 = S_n
```

- **R1 (최종 기록 우선, LWW)**: `결과[k]` = `k`에 non-⊥를 쓴 마지막 프레임의 값, 단 그
  뒤에 `k`의 `⊥`가 없을 때. ⊨ `test_replays_replacements_deletions_and_reinsertion`,
  `test_replacement_keeps_latest_payload`.
- **R2 (fail-closed 전체성)**: 어떤 `f_i`든 길이·CRC·키태그·UTF-8·IV/암호문·PKCS7 중
  하나라도 위반하면 **예외**이며 부분 결과를 내지 않는다(불완전 꼬리 포함).
  ⊨ `test_every_single_byte_corruption_fails`, `test_all_nonempty_truncations_fail_*`.
- **R3 (CRC ≠ 인증)**: seed는 키 불일치·우발 손상을 잡지만 공격자가 재계산할 수 있어
  변조 인증이 아니다. ⊢ 어떤 신뢰 결정도 CRC를 무결성 근거로 쓰지 않는다.
- **R4 (키 유형 분리)**: 정수 키와 문자열 키는 구별된다. ⊨ `test_integer_and_string_keys_are_distinct`.

⊢ **PBT-1**: 임의의 `(키, 값|⊥)` 연산열에 대해 `decode_frames(인코딩(연산열))`가
순수 파이썬 참조 폴드와 **항상** 일치함을 속성 기반 테스트(hypothesis)로 증명.

### 2.2 스냅샷 일관성 — 반례 우선
현재: `read_stable(path)`는 같은 파일을 두 번 읽어 바이트 동일성 확인(단일 파일 torn
read 완화). `snapshot()`은 `folder.hive`·`object.hive`를 읽은 뒤 각 파일을 다시 읽어
변경 없음을 재확인하고, 불일치 시 `StorageError(CHANGED)`. 방 없는 메시지는
`StorageError(ORPHAN)`.

- **반례 C1 (ABA)**: 내용이 A→B→A로 바뀌면 두 동일 읽기가 A여도 중간 B를 놓친다.
  ⊢ 두 읽기의 동일성은 원자 스냅샷을 **증명하지 않는다**(README에 이미 명시).
- **반례 C2 (교차 파일 비원자성)**: `folder`를 t1, `object`를 t2(>t1)에 읽는 사이
  방 삭제+메시지 추가가 나면 참조 불일치가 생긴다. 현재는 ORPHAN으로 **거절**(안전),
  대가는 간헐적 503(가용성 저하).
- ⊢ **P-SNAP**: ABA/교차 파일을 배제하려면 두 파일이 같은 **세대**임을 증명하는 토큰이
  필요하다. 후보: (a) Hive 로그 헤더의 세대/솔트(형식 조사 필요 ⚠), (b) 파일
  `(크기, mtime_ns, 내용해시)` 삼중의 단조 세대 카운터, (c) 복사본을 떠서 단일 시점
  스냅샷. kanao의 "로그 세대로 재사용을 허가"는 **SQLCipher WAL** 기반이라 Hive에
  그대로 적용되지 않는다(⚠ 가정 금지, 별도 검증).
- **결정(소유자)**: C2를 "거절(503)"로 둘지 "세대 토큰으로 정합 보장"으로 올릴지.

### 2.3 계정·세대(epoch) 신원
현재 room id = `sha256(resourceURL)`. ⚠ resourceURL이 계정 간 유일하다고 가정하지
않는다. ⊢ **P-ID**: 재로그인/계정 전환에서 다른 계정의 동일 URL이 같은 id를 받지
않도록 id에 **계정 epoch**(프로필 디렉터리 + 설치 식별자)를 접두로 포함하고, epoch가
바뀌면 커서·스트림을 무효화한다. 불변식: `id = H(epoch ‖ resourceURL)`, epoch 불변 동안
안정, epoch 변경 시 이전 id는 더 이상 유효하지 않음을 응답으로 표현.

### 2.4 미지 버전·어댑터 — 가용성 정책 (결정 필요)
현재: 미지 어댑터 태그 → fail-closed. 버전 센티넬 `version` 정수만 스킵. ⚠ 새
클라이언트가 새 어댑터를 추가하면 **전체 요청 실패**.
- 선택지 A: 계속 fail-closed, 단 버전 비호환을 **명시적 503 + 사유**로(조용한 손실 없음).
- 선택지 B: 미지 레코드를 건너뛰되 응답에 `partial: true`와 누락 수를 노출(조용한 손실
  금지). ⊢ B를 택하면 "건너뜀"이 커서/완전성 주장과 충돌하지 않음을 증명해야 함.
- ⊢ **P-VER**: 어느 쪽이든 "모르는 것을 조용히 삼키지 않는다"는 불변식을 테스트로 고정.

### 2.5 자원 회계
- ⊨ 경계: 파일당 64 MiB, 컬렉션/바이트길이 1,000,000, 중첩 깊이 32.
- ⊨/⚠ `decode_frames`는 파일 전체를 메모리에 올리고 모든 프레임을 디코드 → 비용은
  응답 `limit`과 무관한 `O(Σ 파일 크기)`. `limit`은 **응답 크기만** 제한한다(README 명시).
- ⊢ **P-MEM**: 최대 상주 메모리 상한 `≤ c · Σ(관련 .hive 크기)`를 상수 `c`와 함께
  측정으로 확립. 큰 계정(수십 MB 박스)에서의 상한·지연을 수치가 아니라 **경계 명제**로
  기록(벤치마크 수치 주장 금지, §9).

## 3. 후속 기능 — 작업별 불변식·증명의무·수용기준

각 작업 완료 정의(DoD)는 §6 공통 게이트를 만족해야 한다.

### F1. 페이지네이션 커서 · 스냅샷 만료
- 불변식: 커서는 `(epoch, roomId, 마지막 포함 식별자)`를 담고, 단조 증가하며, **덮은
  출력 뒤에만** 발행된다. 같은 커서 재사용은 같은 경계에서 이어진다.
- ⊢ 커서가 가리키는 스냅샷이 만료(파일 세대 변경)되면 조용히 "지금부터"로 downgrade
  하지 않고 **명시적 신호**로 재동기화를 요구한다(kanao의 "resume 불가는 거절" 규율과 정합).
- 수용: 합성 — 경계에서 끊고 이어도 중복·누락 0. 실패 — 만료 커서는 downgrade가 아니라
  정의된 상태코드.

### F2. SSE 스트림 · 재개(gap 없는 resume) · 멱등 재생 · 삭제≠축출
- 불변식: `event: cursor`는 방별 `{roomId: lastId}`를 **덮은 메시지 뒤**에 보낸다.
  재개는 방별 `since=<roomId>:<id>`로 각 방을 그 지점부터 전진한다. 이름 없는 방은
  "지금부터"이며 그 간극을 **문서화**한다(조용히 메우지 않음).
- 불변식(멱등): 같은 `(epoch, roomId, id)`의 재생은 소비자에서 중복으로 식별 가능.
- 불변식(삭제≠축출): tombstone(삭제)과 캐시 축출(단지 로컬에 없음)을 **다른** 상태로
  표현. 삭제는 R1의 `without k`, 축출은 "모름"이다.
- ⊢ **P-SSE**: 재개가 "놓친 것 없음"을 주장하려면 F1의 세대·커서 불변식에 의존한다.
  세대가 바뀐 재개는 거절 또는 명시적 재동기화.
- 수용: 결정론적 동기화로 테스트(§7) — 이벤트 구독 후 트리거, 고정 sleep 금지.

### F3. 발송 상태 기계 (가장 안전 민감)
상태: `Draft → Submitting → Submitted → {Confirmed | Unknown}`.
- **전제조건**: 대상 방이 현재 스냅샷 세대에 존재, 클라이언트 로그인/입력 가능.
- **정확한 대상**: 방 id로 지정하고 **전송 직전 같은 세대에서 대상 재확인**. 모호하면
  후보를 붙여 거절(첫 매치 임의 선택 금지).
- **draft 보존**: `Submitting` 실패·`Unknown`에서 draft는 사라지지 않는다.
- **submitted ≠ delivered**: 입력창에 넣고 Enter까지가 `Submitted`. 상대 수신은 주장하지
  않는다. `receipt`가 "어디까지 확인되는가"를 선언.
- **uncertain ≠ retryable**: `Unknown`은 **자동 재시도 금지**(중복 발송 위험). 사용자
  명시적 재시도만. ⊢ 자동 재시도 경로가 코드에 **존재하지 않음**을 테스트로 고정.
- **크래시 복구**: 전송 중 크래시 → 재시작 시 `Unknown`으로 표기, 자동 재전송 없음.
- 정합: AGENTS.md "submitted is not delivered", "uncertain send is never retried",
  "Ambiguity is refused with candidates", kanao 발송 규율(입력창 주입·dryRun·되읽기).
- 수용: 합성 상태기계 모델 검증(모든 전이/금지 전이). **실제 발송은 이 계획 범위 밖**,
  사용자 명시 승인과 별도 세션에서만.

### F4. 첨부파일 한계 · 불활성 헤더
- ⚠ 채팅+ 정책(외부 문서): 건별 5MB 비과금, 최대 100MB(안드로이드)/5MB 발송(iOS),
  미다운로드 파일 72시간. ⊢ 실제 로컬 캐시의 첨부 표현을 측정으로 확립 후에만 노출.
- 불변식: 코어는 스트림·타입·이름만 넘기고, 헤더(불활성화: `Content-Disposition:
  attachment`, `X-Content-Type-Options: nosniff` 등)는 전달 계층이 결정. "남의 바이트"를
  실행 가능하게 두지 않는다.

### F5. saya 연동 (계약 게이트 후 최후)
- tsuba 계약이 아니라 **자체 `openapi.json`**(카카오 코어 방식). ⊢ saya가 바이트 핀 +
  SHA-256 고정, 버전 caret 규칙을 통과한 뒤에만 연결. F1(필수), F2·F3(선택) 확정 후.

## 4. 의존성 DAG와 작업 순서

```
B1 스냅샷 세대/일관성(§2.2) ──▶ F1 페이지네이션 ──▶ F2 SSE resume
         │                          │
         ▼                          ▼
B2 계정 epoch 신원(§2.3)       F4 첨부(§F4, F1 이후)
         │
         ▼
F3 발송(동일 세대 대상 확인 필요)

F5 saya ◀── (F1 필수) + (F2·F3 선택) 계약 확정 후
P-VER 미지 버전/어댑터 정책(§2.4)은 B1과 독립, F1 이전에 결정
P-MEM 자원 상한(§2.5)은 독립, 아무 때나 측정 가능
```

순서 근거: 커서·스트림·발송은 모두 "같은 세대"에 의존하므로 B1이 선행. 신원(B2)은
커서·스트림의 키에 들어가므로 F1 이전. saya는 소비 계약이라 맨 뒤.

## 6. 공통 완료 정의(DoD)
각 작업은 다음을 **모두** 만족해야 완료다.
1. `uv run basedpyright` 0 errors.
2. `uv run ruff check chatplus_core tests tools` 통과 + `ruff format --check` 통과.
3. `uv run python -m pytest -q` 단일 실행으로 전부 통과(불안정 금지).
4. 해당 시 실제 경로 검증(`verify_live`/`verify_socket`) 재실행, 개수만 출력.
5. README의 보장 범위·검증 절 갱신.
6. 새 불변식이 **되돌리면 실패하는** 테스트로 고정(프로즈/프롬프트 단언 금지).

## 7. QA 규율
- **속성 기반**: 프레임 재생(PBT-1), 값 디코더(알려진 어댑터/경계/거부). hypothesis.
- **모델 기반**: 스냅샷·발송 상태기계의 전이/금지 전이.
- **결정론적 동기화**: 비동기는 이벤트/배리어를 **먼저 구독**하고 유계 데드라인으로 대기.
  고정 sleep·시간 가정 금지(tests/harness 규율과 정합).
- **스텁은 프로덕션처럼 실패**: 401/429/503/손상 페이로드를 답하는 가짜만 그 경로를 증명.
- **합성만**: 실제 계정 자료 없음. 실제 경로는 개수/상태코드만.

## 8. 실패·롤백 기준
- 세대 토큰(B1)이 Hive에서 신뢰 가능하게 유도되지 않으면 → F1/F2는 "세대 변경 시 거절"
  보수 모드로만 출시하고, 정합 보장은 보류(롤백 아님, 범위 축소를 **명시**).
- 미지 어댑터로 실제 읽기 실패율이 올라가면 → P-VER 결정(A/B)을 사용자에 질의 후 적용.
- 발송(F3)은 실제 전송 승인이 없으면 상태기계·합성까지만. 실제 전송 코드 경로는 비활성.

## 9. 금지된 주장
근거 없이 다음을 주장하지 않는다: exactly-once, 선형화가능성(linearizability),
(CRC를 근거로 한) 인증/무결성, 완전성(전체 phone/server 이력), 인과 순서(causality),
성능 벤치마크 수치. 각 기능 문서는 "무엇을 주장하지 않는가"를 명시한다.

## 12. 1차 기반 조사 결과 (2026-10-03, 실측)

### P-SNAP (§2.2 / §10.1 근거)
- ⊨ 파일 레벨 세대 토큰 없음: `folder.hive`·`object.hive` 모두 오프셋 0부터 프레임으로
  파싱된다(첫 프레임 길이 49). 박스/계정 생성자를 담을 파일 헤더가 존재하지 않는다.
- ⊨ 두 박스 모두 레코드 메타(field 0)에 `lastModSeq` 보유(folder 43, object 140).
  값은 ~나노초 타임스탬프 범위(약 1.72e18 ~ 1.79e18)로, 두 박스가 같은 시계를 쓴다.
- ⚠ 따라서 박스별 `max(lastModSeq)` 워터마크는 (바이트 동일성과 달리) **수정 ABA를
  막는다** — 어떤 쓰기든 `lastModSeq`를 더 큰 값으로 올리므로 되돌림도 새 값으로 남는다.
  단 삭제(tombstone)는 max를 올리지 않을 수 있어 워터마크만으로는 탐지되지 않는다.
  `lastModSeq`의 엄격 단조·시계 단조는 미검증(⊢).
- **§10.1 권고**: C2는 현행 교차파일 ORPHAN 거절(503)을 안전 기본값으로 유지하고,
  향후 박스별 `max(lastModSeq)` 재확인으로 수정 ABA를 강화하되 삭제는 참조무결성
  거절에 계속 의존한다고 명시. (P-SNAP의 부분 해소 + 잔여 ⊢)

### P-MEM (§2.5 근거)
- ⊨ 측정(이 계정, 박스 총 435,249 B): `snapshot()` 중 tracemalloc 피크 67,884,231 B →
  **c ≈ 156** (peak ≈ 156 × 박스 총크기), rooms 43, messages 140.
- ⚠ c는 레코드 수·형태에 따라 달라지는 경험값(이 계정 기준). 피크는 디코드 중 전이
  할당(중간 list/dict/Record/Pydantic 모델)을 포함한다.
- **함의**: 메모리는 `limit`이 아니라 박스 크기에 비례(≈156×). 100 MB급 박스면 수십 GB로
  OOM 위험 → 대형 계정 지원 전 스트리밍/경량 디코드가 선행되어야 함(⊢ P-MEM).

- ⊨ 140개 메시지 모두 Content-Type 보유. 비텍스트 26건(multipart/related 9, GSMA RCS

## 13. 비전송 잔여 작업 판단 (2026-10-03)

- **F5 계약(부분 완료)**: `openapi.json`을 저장소 루트에 공개하고 `tools.dump_contract`로
  재생성, `tests/test_contract.py`가 실행 앱과 바이트 일치를 강제한다. saya가 이 파일을
  핑하면 되므로 saya 측 연결만 남는다(saya 레포 수정은 범위 밖).
- **C2(스냅샷 세대, 보류·근거)**: Hive 박스는 추가 전용(append) 로그라 바이트 동일 이중
  읽기가 모든 실제 변경을 이미 탐지한다(동일 바이트로의 A→B→A는 append 로그에서 불가).
  따라서 `max(lastModSeq)` 워터마크는 두 번째 비싼 디코드를 추가할 뿐 실질 이득이 없어
  **구현하지 않는다**(YAGNI). 재검토 조건: 박스가 추가 전용이 아님이 확인되거나
  체크포인트가 로그를 재작성해 동일 바이트가 재현될 수 있음이 관측될 때.
- **P-MEM(보류·근거)**: 측정상 peak ≈ 156×(박스 총크기). 현재 계정은 작아(피크 68 MB) 문제가
  없다. 대형 계정(수십 MB 박스) 지원이 필요해질 때 스트리밍/경량 디코드를 착수한다.
  지금 최적화는 조기(premature)다. 트리거: 실제 박스 총크기가 메모리 예산을 위협할 때.
- **F3 실제 전송·saya 연결**: 각각 발송/타 레포라 이번 비전송 범위에서 제외.
